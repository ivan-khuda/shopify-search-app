# Phase 8.1: Code Review Report

**Reviewed:** 2026-06-10
**Depth:** standard
**Files Reviewed:** 30
**Status:** issues_found

## Summary

Reviewed all files changed on `gsd/v1-phases-7-8` relative to `main` (phases 7, 8, 8.1) plus uncommitted `app/page.tsx`, at standard depth, with requirement-compliance checks against PROJECT.md constraints (CLAUDE.md). Note: `.planning/REQUIREMENTS.md` referenced in the review brief does not exist; constraints were taken from the PROJECT section of CLAUDE.md.

The headline problem: **the core V1 flow (install → sync → drawer → results) cannot work as shipped.** Two independent Critical defects each break the storefront drawer's bundle load — (1) the bundle URL handed to `loader.js` is scheme-less because two code paths assume contradictory `HOST` formats, and (2) there is no CORS configuration for the cross-origin ES-module `import()` of the bundle from the shop's domain. A third Critical is a requirement violation: storefront visitor identity is an unsigned, client-generated localStorage UUID sent in the request body, where the locked constraint mandates a signed cookie; the per-visitor rate limit is keyed on this client-controlled value.

Positives verified during cross-referencing: `customer_id` is correctly validated server-side against the App-Proxy-signed `logged_in_customer_id` (403 on mismatch), the per-shop monthly cap (`tryConsumeRequest`) gates every chat request, App Proxy routes are wrapped in `withAppProxyHmac`, the `proxy.ts` gate is enabled, no secrets or tokens are logged in any reviewed file, and conversation writes are shop-scoped.

## Critical Issues

### CR-01: Scheme-less bundle URL — `import(m.bundle)` resolves relative to the shop's domain and 404s; drawer can never load

**File:** `extensions/chat-drawer/assets/loader.js:45-47` (manifesting); root cause split across `app/api/proxy/_meta/bundle-url/route.ts:48` and `app/api/auth/callback/route.ts:14` / `lib/shopify/client.ts:9`
**Issue:** The codebase holds two contradictory assumptions about the `HOST` env var format:
- `lib/shopify/client.ts:9` (`hostName: process.env.HOST!`) and `app/api/auth/callback/route.ts:14` (`new URL(\`https://${process.env.HOST!}\`)`) require `HOST` to be **scheme-less** (e.g. `my-app.vercel.app`). If `HOST` contained `https://`, the OAuth callback's `new URL('https://https://...')` throws and `@shopify/shopify-api`'s OAuth URLs break.
- `app/api/proxy/_meta/bundle-url/route.ts:48` does `host.replace(/\/$/, '') + manifest.bundle`, which requires `HOST` to **include** the scheme. With scheme-less `HOST` it returns `{"bundle": "my-app.vercel.app/storefront-bundle-XXXX.js"}`.

`loader.js:47` then runs `import(m.bundle)`. A scheme-less string is a *relative* URL, so the browser resolves it against the storefront page (`https://shop.example/products/my-app.vercel.app/storefront-bundle-XXXX.js`) → 404 → the `.catch` silently resets and the drawer never mounts. There is no `HOST` value that satisfies both code paths, so either OAuth install or the drawer is broken in every environment.
**Fix:** Normalize once. Keep `HOST` scheme-less (the `@shopify/shopify-api` convention) and prepend the scheme in the bundle-url route:
```ts
// app/api/proxy/_meta/bundle-url/route.ts
const host = process.env.HOST?.replace(/^https?:\/\//, '').replace(/\/$/, '');
const bundle = `https://${host}${manifest.bundle}`;
```
Additionally, `loader.js` should defensively reject non-absolute URLs before calling `import()` (e.g. `new URL(m.bundle)` inside the promise chain so a malformed value lands in the existing `.catch`).

### CR-02: No CORS headers on the storefront bundle — cross-origin module `import()` from the shop domain is blocked by the browser

**File:** `extensions/chat-drawer/assets/loader.js:47`, `next.config.ts:6-21`, `scripts/build-storefront-bundle.ts:51-66`
**Issue:** Even with a correct absolute URL (CR-01 fixed), `loader.js` runs on the merchant's storefront origin (`https://shop.example`) and dynamically imports an ES module from the app host (Vercel). Dynamic `import()` issues a CORS-mode module fetch; the response **must** carry `Access-Control-Allow-Origin` or the browser rejects it with a network error. `next.config.ts` defines no `headers()` configuration, and Next.js/Vercel do not add `Access-Control-Allow-Origin` to `public/` static assets by default. The same applies to the esbuild split chunks (`DrawerBody-*.js`, `chunk-*.js`) that the entry chunk imports relatively. Result: the drawer's main bundle never loads from any storefront — the central D-13/D-14 deliverable is dead on arrival. No test covers an actual cross-origin load, so the suite stays green.
**Fix:** Add CORS headers for the bundle and all split chunks in `next.config.ts` (these are public, credential-free JS assets, so `*` is appropriate):
```ts
async headers() {
  return [
    {
      source: '/:file(storefront-bundle-.*|DrawerBody-.*|chunk-.*)\\.js',
      headers: [{ key: 'Access-Control-Allow-Origin', value: '*' }],
    },
  ];
},
```
Verify with a real storefront (or a cross-origin fixture page) before drawer launch.

### CR-03: Storefront visitor identity is an unsigned client-generated localStorage UUID — violates the locked "signed cookie" constraint and lets clients rotate/forge identity

**File:** `lib/chat-ui/adapters/storefront.ts:13-19`, `extensions-src/chat-drawer/entry.tsx:28-39`
**Issue:** PROJECT.md locks storefront identity to "Anonymous visitor (**signed cookie**) with optional customer-id upgrade." The implementation instead generates `crypto.randomUUID()` client-side, persists it in `localStorage` under `smartdiscovery.visitor_id`, and sends it as plain `visitor_id` in the request body. Consequences traced to the server (`app/api/proxy/chat/route.ts:89`):
- The per-visitor rate limit is keyed on `body.visitor_id` — a hostile client bypasses it trivially by rotating the UUID per request (the per-shop monthly cap still applies, but the visitor-level throttle is decorative).
- Any client can claim any `visitor_id`, writing conversations/saved products into arbitrary visitor buckets and — given knowledge of a victim's UUID — reading another visitor's history within the same shop. Nothing server-side attests the identity.
- `mergeVisitorIntoCustomer(shop, body.visitor_id, body.customer_id)` lets a logged-in customer merge any claimed visitor history into their account.

This is an auth-surface requirement violation, not a style choice — the constraint exists precisely so the server mints and verifies the identity.
**Fix:** Mint the visitor id server-side as an HMAC-signed value (e.g. `uuid.sig` using `SHOPIFY_API_SECRET`-derived key) set as a cookie on the first App Proxy response (App Proxy responses can set cookies on the shop domain), and verify the signature in `withAppProxyHmac`-wrapped routes, rejecting unsigned/invalid ids. Keep the localStorage value only as a fallback transport if cookie delivery proves unreliable, but the server must verify the signature either way.

## Warnings

### WR-01: `proxy.ts` gate is an install-check, not authentication; chat page's `shop` falls back to an unvalidated, spoofable query param

**File:** `proxy.ts:5-23`, `app/(embedded)/chat/page.tsx:21-24`, `lib/shopify/server-resolve-shop.ts:15-36`
**Issue:** The gate only checks that `?shop=` is present and that an offline session row exists for that shop. Any anonymous internet user who knows an installed shop's domain passes the gate for `/chat`, `/onboarding`, `/settings`. The W-2 mitigation (`resolveShopFromRequest`) reads the `Authorization` header — but browsers never attach `Authorization` headers to document navigations (App Bridge attaches tokens only to `fetch` calls), so in practice the session-token path never engages for page loads and the spoofable `searchParams.shop` fallback is the de facto resolution path. Two concrete effects: (a) `getActiveChatModel(shop)` performs a cross-tenant `ShopSettings` read for an attacker-chosen shop and leaks the merchant's selected model name in the rendered banner; (b) the unvalidated query value (no `.myshopify.com` suffix check, unlike the session path at `server-resolve-shop.ts:35`) flows into `ChatShell` and DB lookups. Impact is bounded because `EmbeddedAdapter` API calls require `shopify.idToken()` (fails outside the admin iframe), but the page-level gate provides no authentication. The D-09 comment in `proxy.ts` addresses a different question (re-validating `shop` against `session.shop`), not this one.
**Fix:** Minimum: apply the same `.myshopify.com` hostname validation to `shopFromQuery` in `app/(embedded)/chat/page.tsx` before using it. Better: render shop-specific data (model banner) only after client-side App Bridge confirms the session, or verify an HMAC-signed `host`/`id_token` query param (Shopify embeds one on admin iframe loads) in `proxy.ts` before serving shop-scoped content.

### WR-02: `ChatPane.handleSubmit` silently discards attachments and sends an empty message

**File:** `lib/chat-ui/components/chat-pane.tsx:102-117`
**Issue:** When the user submits attachments without text, `hasText` is false and the code falls through to `sendMessage({ text: query })` where `query === ''` — `message.files` is never passed. The result is an empty user message posted to the chat endpoint and the user's attachments silently vanish. The branch exists specifically to handle attachments (`hasAttachments` gate) yet drops them.
**Fix:**
```ts
sendMessage({ text: query, files: message.files });
```
or, if attachments are unsupported by the backend, block submission and surface a notice instead of posting an empty message.

### WR-03: `entry.tsx` `toggle()` is a no-op — drawer cannot be reopened via the loader FAB after closing

**File:** `extensions-src/chat-drawer/entry.tsx:74-80`, `extensions-src/chat-drawer/components/StorefrontDrawer.tsx:34`
**Issue:** The comment says "Re-render with initialOpen toggled" but the code always passes `true`, and `StorefrontDrawer` reads `initialOpen` only as the `useState` initializer — re-rendering the same mounted component with a different `initialOpen` prop changes nothing. So after the user closes the drawer (Escape / close button), a click on the loader-painted FAB calls `toggle()` which does nothing. This is currently masked only because of WR-04 (the React-rendered FAB stacks on top of the dead loader FAB and intercepts clicks) — an accidental dependency, not a design.
**Fix:** Make open state controllable: have `mount`/`toggle` flip a module-level boolean and re-render with a controlled `open` prop (plus `onClose` callback) instead of `initialOpen`, or expose an imperative open/close via a ref. Delete the misleading comment.

### WR-04: loader FAB is never removed after mount — two stacked FABs with duplicate accessible names and stale `aria-expanded`

**File:** `extensions/chat-drawer/assets/loader.js:22-30`, `extensions-src/chat-drawer/entry.tsx:55-72`, `extensions-src/chat-drawer/components/StorefrontDrawer.tsx:66-89`
**Issue:** `loader.js` appends a FAB to `<smartdiscovery-app>`; on first click, `mount()` appends `.sd-drawer-mount` to the same root and `StorefrontDrawer` renders its *own* FAB with the same `sd-fab sd-fab--{position}` class, same fixed position, same `z-index: 2002` (loader.css line ~20 vs inline style). Both buttons coexist permanently: screen readers announce two "Open/Close SmartDiscovery AI chat" buttons, both claim `aria-controls="sd-drawer"`, and the loader FAB's `aria-expanded` is set once to `"false"` and never updated. Which button receives pointer clicks depends on DOM order at equal z-index. Additionally, `loader.js:46` calls `r.json()` without checking `r.ok`, so a 429/500 from the bundle-url route surfaces only as a swallowed parse error.
**Fix:** In `mount()` (entry.tsx), remove the loader FAB before rendering React (`rootEl.querySelector('button.sd-fab')?.remove()`), or have the loader FAB hand off entirely and never render a second FAB from React. Check `r.ok` in loader.js before `r.json()` and route failures to the existing `.catch`.

### WR-05: OAuth callback: no error handling around `auth.callback`, `process.env.HOST!` assertion, fragile `localhost` substring check

**File:** `app/api/auth/callback/route.ts:5-20`
**Issue:** (a) `shopifyClient.auth.callback()` throws on invalid HMAC/state (which *will* happen — e.g. replayed or tampered callback URLs); unhandled, this becomes a raw 500 with a framework stack trace rather than a controlled 400/redirect. (b) `process.env.HOST!` non-null assertion produces the literal string `"https://undefined"` → `new URL` succeeds and redirects users to a dead host when `HOST` is unset, instead of failing loudly like the online callback does (`online/callback/route.ts:12-14` returns a clear 500). (c) `request.url.includes('localhost')` matches anywhere in the URL (e.g. `?shop=localhost...`-style values or any param containing "localhost"), a fragile heuristic for environment detection.
**Fix:** Wrap `auth.callback` in try/catch returning a 400 with a generic body; check `HOST` explicitly like the online callback does; gate the dev rewrite on `new URL(request.url).hostname === 'localhost'` (or `process.env.NODE_ENV !== 'production'`).

### WR-06: `retryId` interpolated into status URL without `encodeURIComponent`

**File:** `app/(embedded)/onboarding/page.tsx:76`
**Issue:** `fetch(\`/api/shopify/sync/status?syncRunId=${retryId}\`)` — `retryId` comes straight from `?retry=` in the URL. A crafted deep-link (e.g. from a tampered email link) containing `&`/`#` injects additional query parameters into the request or truncates it. Exploitability is low (Bearer-authed, server validates the id), but it is unsanitized user input concatenated into a URL.
**Fix:** `\`/api/shopify/sync/status?syncRunId=${encodeURIComponent(retryId)}\``.

### WR-07: Drawer panel ignores the merchant's `position` setting and uses a fixed 400px width

**File:** `extensions-src/chat-drawer/components/StorefrontDrawer.tsx:95-106`
**Issue:** The `<aside>` is hard-coded `right: 0` regardless of `position`. A merchant who selects "Bottom left" in the theme editor gets a left FAB but the drawer slides out on the right side of the screen. Separately, `width: 400` with no `maxWidth: '100vw'` overflows viewports narrower than 400px (a large share of storefront traffic is mobile).
**Fix:** Mirror the FAB logic: `[position === 'bottom_right' ? 'right' : 'left']: 0`, and add `width: 'min(400px, 100vw)'`.

### WR-08: `shopify.app.toml` committed with ngrok dev-tunnel URLs as the app's production config

**File:** `shopify.app.toml:5,18-24`
**Issue:** `application_url`, both `redirect_urls`, and the `app_proxy.url` all point to `https://fdef-194-212-224-20.ngrok-free.app` — an ephemeral dev tunnel. Deploying this config (`shopify app deploy`) breaks OAuth, the embedded app URL, and the App Proxy for every merchant the moment the tunnel dies. Free-tier ngrok hosts are also re-assignable to other users, meaning a third party could transiently receive OAuth callbacks for the configured app.
**Fix:** Keep the dev tunnel in a `shopify.app.dev.toml` (CLI `--config` flag) and commit a production config with stable URLs, or document an enforced pre-deploy step that rewrites these values. At minimum, do not merge tunnel URLs to `main`.

### WR-09: `bundle-build.test.ts` has vacuous pass paths and selects the "latest" bundle lexicographically

**File:** `__tests__/bundle-build.test.ts:59-66,100-125`
**Issue:** (a) The manifest test wraps `execSync('bun run prebuild')` in a bare `catch {}` (lines 59-66) — if prebuild fails but a *stale* manifest exists from a previous run, the test validates the stale file and passes. (b) The size test picks `bundleFiles.sort().pop()` — content hashes (`5CU7SDYB`, etc.) have no temporal ordering, so with more than one `storefront-bundle-*.js` present (e.g. cleanup regression) it can measure an arbitrary stale file and pass while the real entry exceeds budget. (c) Several early-return `expect(true).toBe(true)` branches (lines 103, and the `readdirSync` catch) convert error conditions into passes. The D-14 budget gate is therefore not a reliable gate.
**Fix:** Run prebuild once in a `beforeAll` that fails the suite on error; read the entry path from `storefront-manifest.json` (`manifest.bundle`) instead of sorting directory listings; remove the vacuous `expect(true)` branches now that the implementation exists (the RED-scaffold escape hatches have outlived their purpose).

### WR-10: Unguarded `localStorage` access crashes mount / chat send when storage is blocked

**File:** `extensions-src/chat-drawer/entry.tsx:30-37`, `lib/chat-ui/adapters/storefront.ts:14-17`
**Issue:** `window.localStorage.getItem/setItem` throws `SecurityError` in browsers with site-data blocked (Safari "Block all cookies", some embedded webviews, certain private modes). In `entry.tsx`, the throw happens inside `mount()` → `renderDrawer()` → `resolveVisitorId()`, unwinding the whole mount: the bundle loaded but the drawer never appears and the skeleton class was already removed. In the adapter, every `getRequestBody()` rejects, breaking chat sends. Storefront code runs on thousands of uncontrolled browser configurations; this needs a fallback.
**Fix:** Wrap storage access in try/catch and fall back to an in-memory (per-page-load) UUID:
```ts
function safeGet(k: string): string | null { try { return window.localStorage.getItem(k); } catch { return null; } }
```

### WR-11 (cross-file, outside listed scope): conversation persistence overwrites history instead of appending, and `conversation_id` ownership is not visitor-checked

**File:** `app/api/proxy/chat/route.ts:103-104,162-177`
**Issue:** Found while tracing the StorefrontAdapter request path. (a) The `onFinish` handler builds `newTurns` from only the *latest* user message + response and writes `data: { messages: newTurns }` — a Prisma `Json` column **replace**, not an append, despite the adjacent comment claiming "atomic single-row append (D-19)". Every multi-turn conversation's persisted history is truncated to the last exchange; any conversation-resume or history-detail feature reading `Conversation.messages` returns incomplete data. (b) When the client supplies `body.conversation_id`, it is used directly (line 103-104) and the update `where` is `{ id, shop }` only — not scoped to `visitorId` — so any same-shop client who learns another visitor's conversation cuid can write turns into it (compounded by CR-03's forgeable visitor identity).
**Fix:** (a) Append atomically via raw SQL (`jsonb || jsonb`) or read-modify-write inside a transaction; or, if storing only the last exchange is intentional, fix the comment and confirm no reader expects full history. (b) Validate `conversation_id` ownership: `where: { id, shop, visitorId: body.visitor_id }` (or pre-fetch and 403 on mismatch).

### IN-02: Build script uses `require('node:fs')` despite ESM imports; broad cleanup regex

**File:** `scripts/build-storefront-bundle.ts:37,46`

### IN-07: Liquid comment claims auto-escaping that Shopify Liquid does not perform

**File:** `extensions/chat-drawer/blocks/app_embed.liquid:11-13`

### IN-08: `crypto.randomUUID` newer than the es2020 build target

**File:** `extensions-src/chat-drawer/entry.tsx:35`, `lib/chat-ui/adapters/storefront.ts:16`, `scripts/build-storefront-bundle.ts:56`
**Issue:** The bundle targets `es2020` (broad browser reach), but `crypto.randomUUID` ships only in Chrome/Edge 92+, Firefox 95+, Safari 15.4+ and requires a secure context. On older storefront browsers it throws and the drawer mount fails. Marginal population, but the syntax target implies broader support than the API provides.
**Fix:** Feature-detect with a `getRandomValues`-based fallback.
