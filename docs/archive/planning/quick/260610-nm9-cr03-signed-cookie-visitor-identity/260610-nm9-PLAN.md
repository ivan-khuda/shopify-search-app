<objective>
Fix CR-03: replace the client-minted, unsigned `localStorage` visitor UUID with a
server-minted, HMAC-signed visitor identity that the server verifies on every
storefront App Proxy request. Today the server trusts `body.visitor_id` /
`?visitor_id=` verbatim — so the per-visitor rate limit is forgeable (rotate the
UUID per request) and any same-shop client can read/write another visitor's
conversations and saved products by guessing/learning their UUID. The locked
PROJECT.md constraint mandates "Anonymous visitor (signed cookie) with optional
customer-id upgrade." This makes the identity server-attested and unforgeable
while keeping zero-login anonymity.

Purpose: Close the auth-surface requirement violation (CR-03) so the per-visitor
throttle and per-visitor data scoping become enforceable, not decorative.

Output: Server signing helper + verification wired into the App Proxy auth layer,
a mint/bootstrap endpoint, all five storefront proxy routes keying on the
verified id, and the client layers (adapter + DB-backed stores + entry bootstrap)
rewritten to consume the server-signed token. All ~9 affected test files updated.

CRITICAL TRANSPORT NOTE (read before implementing):
Shopify App Proxy STRIPS both `Set-Cookie` and `Cookie` response/request headers
(confirmed against shopify.dev "Disallowed App Proxy Response Headers"). A literal
HTTP cookie set on the shop domain — as CR-03's suggested fix text proposes — is
IMPOSSIBLE through the App Proxy boundary. This is also why the original team chose
localStorage (STATE.md decision: "localStorage for visitor_id — App Proxy strips
Set-Cookie"). We therefore deliver the *security intent* of the "signed cookie"
constraint — a server-minted, server-signed, server-verified identity token — using
the only durable transport App Proxy permits: a signed token in the JSON body,
persisted client-side. The signature (HMAC-SHA256 keyed on a SHOPIFY_API_SECRET-
derived key) is what makes the id unforgeable and closes the vulnerability; the byte
on the wire being a body token rather than an HTTP cookie does not weaken the
security property. Document this deviation in code comments where the constraint is
implemented (per D-? deviation-logging convention used elsewhere in this codebase).
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| storefront browser → App Proxy → /api/proxy/* | Untrusted client supplies visitor_id; Shopify HMAC-signs shop+logged_in_customer_id but NOT visitor_id |
| client localStorage | Fully attacker-controlled; any stored token is suspect until server-verified |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-nm9-01 | Spoofing | visitor identity on all 5 proxy routes | mitigate | verifyVisitorId (HMAC) before rate-limit/DB; reject unsigned/tampered with 401 invalid_visitor_signature (Task 2) |
| T-nm9-02 | Tampering | per-visitor rate-limit key (rateLimit(body.visitor_id)) | mitigate | key on server-verified uuid only; rotating the UUID no longer mints a fresh bucket because forged ids 401 (Task 2) |
| T-nm9-03 | Information Disclosure | cross-visitor conversation/saved-product read within a shop | mitigate | ownership scoping already by visitorId; now the visitorId is unforgeable so the scope is real (Tasks 1+2) |
| T-nm9-04 | Elevation of Privilege | mergeVisitorIntoCustomer on a claimed visitor id | mitigate | merge runs only for a verified visitor uuid; customer_id still cross-checked against signed logged_in_customer_id (existing) |
| T-nm9-05 | Info Disclosure | signature/secret leakage in logs | mitigate | no console.* of token/signature/secret anywhere (PROJECT.md hard constraint; existing pattern) |
| T-nm9-06 | DoS | unauthenticated mint endpoint spamming /_meta/visitor | accept | per-shop 'read' rate-limit bucket on the mint route; minting is cheap (HMAC, no DB); matches existing bundle-url route posture |
